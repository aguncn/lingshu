# 技能：故障诊断与处置报告（o2-sre-report）

> 适用：诊断到了收尾阶段——把日志/指标/链路/审计证据收敛成“根因 + 处置 + 建议”的报告。
> 目标：像值班 SRE 交班一样：结论有据、可复核、可执行，不含糊、不编造。

## 流程
1. **重述证据**：列你实际跑过的查询与关键命中（每类 1–2 条即可）：
   - 日志：哪条 SQL / 关键字 / 命中数（例：`message like '%pool exhausted%'` 15 条，service=ec-order）；
   - 指标：哪个 family 的趋势与量级（例：`ec_db_conn_pool_waiting` 0→8、active 顶到 max）；
   - 链路：trace_id + 出错 span 的服务/操作；
   - 审计：`ec_audit_logs` 里对应变更（`fault_id` / actor·action·detail）。
2. **检索知识库对样**：调 `knowledge_search` 查 `fault-F*` runbook（或读挂载的资料库速查），把当前现象与历史故障**特征比对**（命中相似=增强置信；不像=说明差异）。
3. **下结论**：
   - 根因一句话 + 证据链；区分“现象”（如 429）与“根因”（如连接池打满/上游剔除）。
   - 置信度：证据充分→高；只有单类信号→中并指出还需补什么；信号不足→明说“信息不足以定位”，列出要补的查询。
4. **给处置**：按 runbook 的下一步（回滚/扩容/清积压/重启/续证书/清 CDN…），标注影响与先后。
5. **给验证**：修复后看哪个指标/关键字应回落，何时复核。

## 报告模板（建议照此输出）
```markdown
## 诊断结论
- 故障：<是什么；疑似/确认>
- 影响：<服务/接口/时间段/量级>
- 证据：
  - 日志 SQL「…」→ …
  - PromQL「…」→ …
  - trace「…」→ …
  - 审计「…」→ …
- 与 runbook 比对：F? 特征命中/未命中（说明）
- 根因：<一句话，附证据链>
- 处置：1)… 2)… 3)…
- 验证：<修复后应观察到的回落信号 + 复核时机>
```

## 红线
- **每句结论都能指到一条工具结果**；编造字段/数字/曲线 = 事故。拿不到就说拿不到。
- 不把“告警少了”当“修好了”——要看根本信号是否回落。
- 报告语言精炼、面向值班交接，别贴原始日志刷屏。
