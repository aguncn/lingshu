# 02 · 数据生成与核对

## 命令形态

```bash
uv run python sim/main.py --help                     # 全部选项
uv run python sim/main.py                            # 默认：最近 3 天 + F1 live(近45分钟) + 能放下的历史故障
uv run python sim/main.py --hours 3                  # 短窗快速演示（默认 5h 灌入限制内，可直接跑）
uv run python sim/main.py --days 7 --live-fault F3   # 7 天回填(需放宽灌入限制)，F3 打 live
uv run python sim/main.py --faults F2,F5 --history none --live-fault F2   # 只放指定的两条(其一 live)
uv run python sim/main.py --faults none --history none --hours 2          # 纯干净基线，不放任何故障
uv run python sim/main.py --end 2026-09-07T14:30     # 精确指定结束时刻
uv run python sim/main.py --purge-own                # 先清上次 ec_* 数据再灌（幂等重跑）
```

关键参数：

| 参数 | 含义 |
|---|---|
| `--end` | 结束时刻（含），默认 = 当前时间 −1 分钟 |
| `--days` / `--hours` | 往前回填的时间范围；两者互斥 |
| `--seed` | 随机种子（默认固定 → 每次结果可复现） |
| `--faults` | `all` / `none` / 逗号列表如 `F1,F3` |
| `--live-fault` | 作为 **live**（贴现在、触发告警）的故障，默认 `F1`；`none`=不要 live |
| `--history` | 历史故障 `auto`（能放下多少放多少）/ `none` |
| `--purge-own` | 只删 `ec_*` 自身流并等删除落定（仪表盘保留、同名自动更新），不碰旧数据，再重灌 |

### 故障怎么落窗口
- **live 故障**：窗口 = `[end−故障时长, end]`，即灌完的最后一小段，紧贴现在 → 建好告警后数分钟内即可触发。
- **历史故障**：从 live 窗口往前、按固定顺序 F1→F2→… 由近及远排，每个之间留 20 分钟空隙；窗口不够就跳过并打印“剩余窗口不足”。
- 也就是说：**窗口越长能放的故障越多**。短窗（几小时）可能只放得下 1~2 条历史故障 + 1 条 live，属正常。

## 多天回填：放宽 O2 的历史灌入限制

默认 O2 只接收最近约 5 小时的数据；回填超过会直接拒绝（报 `ZO_INGEST_ALLOWED_UPTO`）。解决（在**跑 O2 的那台机器/WSL** 上操作）：

1. 找到启动 O2 的地方（docker compose 的 `environment:` 或 docker run 的 `-e`），加一行：
   ```yaml
   environment:
     - ZO_INGEST_ALLOWED_UPTO=120     # 允许回填最近 120 小时(=5天)；按窗口给够即可
   ```
2. 重启 O2（`docker compose down && docker compose up -d` 或等价的 stop/start）。
3. 重跑生成。

> 改完先用 `uv run python selftest.py --oldest <要回填的最早时间>` 探一眼，确认服务端已放行。

## 灌入之后：怎么核对真的成功了

main.py 结束会打印各流条数 + 抽样 count；之后去 O2 界面核对（记得把**时间范围**选成你的数据窗口）：

| 看什么 | 在 O2 哪里 | 期望 |
|---|---|---|
| 日志 | **Logs** 页左侧选 `ec_access_logs` 等 6 个流 | 有 INFO/WARN/ERROR、服务 `ec-*`、主机 `ec-*`，能看到 trace_id/span_id |
| 指标 | **Metrics** 页 PromQL（如 `ec_http_request_rate`、`ec_kafka_consumer_lag`） | 有序列、能出折线 |
| 链路 | **Traces** 页，按 `service_name` 过滤 `ec-*` | 瀑布图；故障时段含 ERROR span |
| RUM | Logs 页 `ec_rum_pageview` / `ec_rum_error` | PV 行带 `lcp_ms/ttfb_ms/route/dist_version`；error 行带 `error_type` |
| 仪表盘 | **Dashboards** 页，找 `E-commerce …` 4 张 | 面板能出图（若空：等 1~3 分钟点刷新） |
| 告警 | **Alerts** 页 | 按 `docs/03` 手工建 F1 规则后，live 窗口数分钟内触发 |

### 三个“版本事实”导致的核对姿势（本 O2 实测）
1. **指标有 1~3 分钟异步索引**：刚灌完查 PromQL/开面板偶发空白/不全 → 等一两分钟再刷新即稳定（selftest 与 main 已按此写死等待）。
2. **追踪不能 SQL 查**（`Search stream not found` 属正常）：用 Traces 页或 MCP GetLatestTraces。
3. **仪表盘 API 可建**：生成时会自动 upsert 同名 `E-commerce …` 仪表盘（v0.92 v8 schema，面板已实测可落盘）；老版本不行时也可把 `dashboards/*.json` 拿到 O2 Dashboards→New/Import 界面导入。

## 想清空重来（只清自己的数据）

```bash
uv run python sim/main.py --purge-own --hours 2 --faults none
```

- 只删 `ec_*` 流并**等删除落定**（自动处理 O2 删流异步、灌入自动重试）；同名仪表盘**保留并自动更新**（按标题 upsert，不删库重建）。**绝不碰** `fin_* / tel_* / rum_data` 等旧数据。
- O2 删流/删仪表盘为异步，偶见列表残留空流属正常。
- **日志流删流由 O2 后台按周期批量落定**（本实例实测：一轮批量可能 ~1 小时；周期内流从列表消失、但同名仍报 `is being deleted`，要等下一轮批量放掉；指标流则快）。脚本每 60s 打心跳、**全部就绪即提前开始灌入**；默认预算 75 分钟≈覆盖一轮批量，仍超时才判异常**明确终止**。**已排队的删除不会因重跑而重置**——等不及可 Ctrl+C，隔一阵重跑本命令，删除照常落定、数据自动补齐。

## 数据量参考
- `--hours 3`：约 4 万行日志、近万个指标点、数千 span，几十 MB 内，本地 O2 毫无压力。
- 更长的天窗：日志按日波动曲线自动削峰（深夜低、白天双高峰），不会线性爆炸。
