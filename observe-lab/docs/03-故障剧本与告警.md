# 03 · 故障剧本与告警

observe-lab 内置 **6 条故障**（F1–F6），每一条都：
- 在模拟数据里产生**真信号**（错误日志关键字 / PromQL 特征 / 链路 ERROR span / RUM 报错），不是写死标题；
- 有一份与之配套的 `alerts/alert-F*.json` 规则定义（本 O2 版本 REST 建规则不可用 → **在 UI 手工填**，见下）；
- 有一页 runbook：`qa/fault-F*.md`（同名也导出到 `exports/lingshu-kb/`，供灵枢知识库检索）。

## 六条故障一览

| 故障 | 级别 | 影响面 | 时长 | 一眼定位关键字 | 对应告警规则名 |
|---|---|---|---|---|---|
| **F1** 订单库连接池耗尽 / 慢 SQL | P1 | ec-order / ec-payment / ec-gateway / MySQL | ~45 分 | `ER_LOCK_WAIT_TIMEOUT` `pool exhausted` `query too slow` `circuit OPEN` | `ec_F1_订单库连接池耗尽或慢SQL` |
| **F2** Redis 热点键击穿 / 缓存雪崩 | P1 | ec-product / ec-inventory / ec-cart / Redis | ~45 分 | `cache stampede` `MISS burst` `evicting keys` `db read amplification` | `ec_F2_Redis热点键击穿缓存雪崩` |
| **F3** 支付回调 Kafka 消费积压 | P1 | ec-payment / ec-order / Kafka | ~50 分 | `lag=` `state still pending` `max.poll.interval` | `ec_F3_支付回调Kafka消费积压` |
| **F4** 网关误限流 + 上游单实例剔除 | P1 | ec-gateway / ec-product / ec-order | ~40 分 | HTTP `429/502/503`、`upstream` refused | `ec_F4_网关误限流+上游剔除` |
| **F5** 节点磁盘 90% + 外呼证书过期 | P2 | ec-node-2 / ec-web / ec-payment(外呼 HTTPS) | ~50 分 | `No space left` `disk pressure` `certificate has expired` | `ec_F5_节点磁盘90%+证书过期` |
| **F6** 前端发版引入 JS 报错 | P2 | ec-web（RUM：`/` 与 `/checkout`） | ~40 分 | `app.7f3a.chunk.js` 404、`Cannot read properties`、`Uncaught (in promise)` | `ec_F6_前端发版JS报错` |

每条故障的**完整症状清单 / 该查的 SQL·PromQL / 根因 / 处置 / 提问话术**，见 `qa/fault-F1.md … fault-F6.md`（或知识库导入后的同名文档）。上文关键字都真实出现在对应故障窗口的日志里，可直接在 O2 Logs 页全文搜。

## 故障怎么落窗口（决定“现在能不能看到/触发”）

- **live 故障**：窗口 = `[灌入结束时刻 − 故障时长, 灌入结束时刻]`，即最后一段紧贴“现在”。默认 F1 是 live。
- **历史故障**：从 live 窗口往前、按 **F1→F2→…→F6** 固定顺序由近及远排，两条之间留 **20 分钟**空隙；剩余窗口不够就跳过并打印“剩余窗口不足”。
- 结论：**窗口越长，放得下的故障越多**。想看某条历史故障，把回填范围拉到覆盖它；`--faults`/`--live-fault` 可精确指定放哪几条。

示例：

```bash
uv run python sim/main.py --hours 3 --live-fault F4     # F4 贴现在(短窗)：3小时内能放下 live + 1~2 条历史
uv run python sim/main.py --days 7 --live-fault F3      # 7天窗(需放宽灌入限制，见 docs/02)：6 条都能放下，F3 贴现在
```

> 灌完想查某条故障：在 O2 把时间范围选到它的窗口，用上表的“一眼定位关键字”全文搜即可命中。面板/指标要等 1~3 分钟索引追上才最稳。

## 每条告警规则长什么样

下面六张表 = `alerts/alert-F*.json` 里 `ui` 字段的值，直接照抄即可。**统一规则**：数据源=日志流、统计=`count(*)`、窗口=**15 分钟**、评估=**每 5 分钟**、静默=0 分钟。

| 规则 | 数据源(日志流) | 匹配条件（SQL where） | 触发 |
|---|---|---|---|
| `ec_F1_…` | `ec_application_logs` | `service in ('ec-order','ec-payment') and level='ERROR' and (message like '%pool exhausted%' or message like '%ER_LOCK_WAIT_TIMEOUT%' or message like '%query too slow%' or message like '%full table scan%')` | `count(*) >= 5` |
| `ec_F2_…` | `ec_application_logs` | `service in ('ec-product','ec-inventory','ec-cart') and (message like '%cache stampede%' or message like '%MISS burst%' or message like '%db read amplification%' or message like '%evicting keys%')` | `count(*) >= 8` |
| `ec_F3_…` | `ec_application_logs` | `service='ec-payment' and (message like '%lag=%' or message like '%state still pending%' or message like '%max.poll.interval%')` | `count(*) >= 10` |
| `ec_F4_…` | `ec_access_logs` | `(status in (429,502,503)) and (path like '%checkout%' or path like '%orders%')` | `count(*) >= 30` |
| `ec_F5_…` | `ec_system_logs` | `(message like '%disk%' or message like '%No space left%' or message like '%certificate%') and level in ('WARN','ERROR')` | `count(*) >= 5` |
| `ec_F6_…` | `ec_rum_error` | `service='ec-web' and level='ERROR'` | `count(*) >= 15` |

> `ec_access_logs.status` 是**整数**，写规则时用 `status in (429,502,503)` 不要加引号（加了会匹配不到）。上面 SQL 均可用「目标 SQL 生成」按钮回填，或直接在 Logs 页验证。

## 在 O2 UI 手工建规则（本版本唯一通道）

本 O2（v0.92.2）**没有 REST 建告警规则的可用接口**（`alerts` CRUD 一律 404/405），但告警引擎本身正常，规则在 **Alerts 页面**手工建、建完对 live 窗口**数分钟内可触发**。步骤（各版本菜单位置略有差异，按名字找即可）：

1. 打开 O2 → 左侧 **Alerts**。
2. 点 **New Alert / 新建规则**，规则名填 `ec_F1_订单库连接池耗尽或慢SQL`（抄上表，或打开 `alerts/alert-F*.json` 看 `name`）。
3. **数据源**选对应日志流（如 `ec_application_logs`）；把该规则的 SQL 填进条件（大部分 UI 有「目标 SQL」文本框，把整句 `select count(*) as count from "ec_xxx" where …` 粘进去最稳；没有就用 where 片段）。
4. **触发条件**：窗口/period = 15 分钟，`count(*) >= <上表阈值>`，评估周期 = 每 5 分钟。
5. 保存。先别急着关 —— 看下一条的评估拍点，见下节。

> 说明：`alerts/alert-F*.json` 里的 `ui` 字段就是给这一步的“填空值”；`suggest_check` 是触发后该去哪核对（哪张 PromQL / 哪些关键字）。REST 不可用这一点在灵枢侧兜底：SRE 专家改走「查告警」= 用 PromQL/日志关键字**反查现场**，而不是调 O2 的 alert CRUD（见 docs/04）。

## 让告警数分钟内触发（live 工作流）

1. 先**建好**你想要的规则（至少 F1 那条）。
2. 再生成数据，并让该故障做 **live**：`uv run python sim/main.py --hours 2 --live-fault F1 --faults F2,F3`（live 窗口紧贴灌入结束时刻 = 现在）。
3. 因为规则是**向前看 15 分钟**、每 5 分钟评估一次，灌完后的**下一次评估拍点**就会把 live 窗口里的错误日志数进来 → 规则立刻进入 triggered，Alerts 页列表在几分钟内能看到该规则红/告警态。

> 想让演示“现建规则 → 立刻见触发”，就把 live 故障留到你**建好规则之后**再灌。灌完即触发，是最有现场感的一条路径。

## 收到告警后去哪核对

每条故障的核对路径都在 `qa/fault-F*.md`，统一节奏：

1. **拉现场**：按 `alerts/*.json` 的 `suggest_check`，Logs 搜关键字 / PromQL 拉对应指标（如 F1 看 `ec_db_conn_pool_waiting`、F3 看 `ec_kafka_consumer_lag`）。
2. **看审计找变更**：到 `ec_audit_logs` 按时间窗查 deploy/配置变更（`F*_部署/变更` 消息），对上“为什么会发生”。
3. **下结论**：命中 runbook 的“疑似根因 / 处置步骤”，给出一句话结论。这套动作就是灵枢 SRE 专家在演示里做的（docs/06）。

六条故障各自的特异诊断链路（要查哪个 metric、哪句审计、答什么）在 docs/06 里给了端到端提问样例。
