# 00 · 总览与流程

observe-lab 做三件事，给灵枢「模拟故障智能诊断」当真实数据源：

1. **模拟一家电商企业的线上可观测数据**（日志/指标/追踪/RUM），写入你自托管的 OpenObserve，时间范围可指定。
2. **内置 6 条真实感故障**（F1–F6），生成对应症状信号 + 可触发的告警规则；每条都有 runbook 和“一问一查一对”的诊断链路。
3. **给灵枢侧一整套接入物**（MCP 连接 / SRE 专家 / 技能 / 知识库 / 资料库 + 导入脚本/清单）与**实践指导文档**，让你照着就能跑起来一轮真实诊断演示。

## 建议流程

```
① 填 .env（docs/01）   →  ② selftest 自检（docs/01）
③ 生成数据（docs/02）   →  ④ 在 O2 核对 + 建告警看触发（docs/02、03）
⑤ 导入灵枢（docs/04、05 + exports/）   →  ⑥ 实战诊断演示（docs/06）
```

## 想一次看懂的三个概念

- **命名空间 `ec_`**：日志流、指标名、服务名、仪表盘、告警都带 `ec-`/`ec_`，和你 O2 里已有的旧数据彻底隔离，`--purge-own` 只清 `ec_*`。
- **live 故障 vs 历史故障**：live 故障的窗口紧贴“当前时刻”（灌完数分钟内即可触发告警、在告警页看到）；历史故障填在更早窗口，靠仪表盘/日志时间范围翻看。默认 F1 是 live。
- **每类信号在哪看**：

| 信号 | O2 落点 | 备注 |
|---|---|---|
| 日志 | Logs 页 / SQL 查询 | `ec_access_logs` 等 6 个流；`_timestamp` 微秒 |
| 指标 | Metrics 页（PromQL） | OTLP gauge，`ec_*` family；灌完等 1~3 分钟索引追上最稳 |
| 链路 | Traces 页 | OTLP 落 `default` traces 流，按 `service_name ec-*` 过滤 |
| RUM | Logs 页的 `ec_rum_pageview/ec_rum_error` | 前端体验用日志流表达（web vital 字段在记录里） |
| 仪表盘 | Dashboards 页 | `E-commerce …` 4 张，生成时自动 upsert，也可 UI 导入 |
| 告警 | Alerts 页 | 本 O2 版本 REST 建告警不可用 → 用 `alerts/*.json` 在 UI 手工建（docs/03） |

## 目录速查

见 `README.md` 的目录注释；故障说明在 `docs/03` + `qa/fault-F*.md`，灵枢导入在 `docs/04/05` + `exports/`。

## 三句话提醒（重要事实）

1. 默认 O2 只允许灌最近约 **5 小时**的数据；要多天回填需设 `ZO_INGEST_ALLOWED_UPTO` 并重启（`docs/02`）。只想先看效果就用 `--hours 3`。
2. 本 O2 的 **REST 告警建规则接口 404**，所以告警规则走 **UI 手工建**（`alerts/*.json` 已给你每个字段的填写值）；仪表盘走 **API 自动建**（v0.92 v8 schema，已修好并验证面板可落盘）。
3. 链路走 OTLP、落 O2 的 `default`(traces) 流，**不能用 SQL 查 trace**，请在 Traces 页 / MCP GetLatestTraces 里核对（`service_name` 以 `ec-` 开头）。
