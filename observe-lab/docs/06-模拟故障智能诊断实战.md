# 06 · 让灵枢做一轮「模拟故障智能诊断」实战

前提：`docs/01→05` 都做完 —— O2 有数据（含一条 **live 故障**贴着现在），灵枢已导入 MCP/SRE 专家/知识库/资料库，
并在一个任务上应用了「SRE 值班专家·observe-lab」。本文给 6 条故障各自的**演示剧本**：你问什么、模型“应该”怎么查、期望结论是什么。

## 先决定演哪条故障
```bash
uv run python sim/main.py --hours 2 --live-fault F4 --faults F2,F3    # 例：F4 贴现在(live)，F2/F3 放历史
```
- 想让“告警数分钟内触发→再让模型查”，就先把该故障的告警规则建好（docs/03）**再**跑上面的灌数。
- 想连续演示多条，就选长窗 + 把要演的设 live 一条条来；或让模型直接对着某**历史故障窗口**做“复盘式诊断”（在提问里给出时间窗）。

## 通用：怎么判断模型“真的在诊断”
| 项 | 好 | 差 |
|---|---|---|
| 用工具 | 提问后模型调了 O2 MCP（SQL/PromQL/GetLatestTraces），能看到工具往返 | 不查直接长篇结论 |
| 引证据 | 结论带“哪句查询/关键字/命中数/曲线形状” | 只有“疑似/可能”空话 |
| 字段名 | 用的是 `ec_*` 真流名/真 metric（必要时先 StreamSchema/查速查） | 编了不存在的流/metric |
| 对样 | 命中知识库 fault-F*（提到 runbook 根因或处置） | 无视知识库 |
| 收尾 | 给根因一句话 + 处置 + “修复后看什么回落” | 停在现象层 |

## 剧本一 F1 订单库连接池耗尽 / 慢 SQL（P1 · live 默认）
- **现场**：O2 Alerts 里 `ec_F1_…` 已触发（或你在值班消息里说“下单在超时”）。
- **问**：“现在下单和支付接口大面积超时，P99 飚了，帮我定位根因并给出处置。”
- **模型应做**：`ec_application_logs` 搜 `pool exhausted/ER_LOCK_WAIT_TIMEOUT/query too slow` → `ec_db_conn_pool_active{component="ec-order-db"}` 顶到 max、`ec_db_conn_pool_waiting`>0 → `ec_audit_logs` 看到 `fault_id=F1` 的 DDL 建索引 + 报表任务 → 知识库 `fault-F1` 对样。
- **期望结论**：订单库连接池耗尽；疑似 DDL+全表扫描报表把连接占满 → 处置：EXPLAIN 订单查询、停报表/回收连接；验证：`waiting` 归零、p99 回落。

## 剧本二 F2 Redis 热点键击穿 / 缓存雪崩（P1）
- **现场**：商品页卡、缓存命中率告警。
- **问**：“商品详情页很慢，缓存命中率掉了，查一下是不是缓存出了问题。”
- **模型应做**：`ec_redis_hit_ratio` 从 ~95% 掉到 ~45% → `ec_mysql_qps{component="ec-shop-db"}` 冲高（回源）→ 应用日志 `cache stampede/MISS burst/evicting keys` → 审计里有改 `maxmemory-policy=allkeys-lru` → 对样 `fault-F2`。
- **期望结论**：热点 key 击穿 + LRU 整片回源 → 处置：热点加逻辑过期/互斥重建、补预热、回滚策略；验证：命中率回升、DB QPS 回落。

## 剧本三 F3 支付回调 Kafka 消费积压（P1）
- **现场**：支付成功但订单“状态仍处理中”，业务侧压测反馈。
- **问**：“一批已支付订单状态一直不更新，后端没报 5xx，查一下卡在哪。”
- **模型应做**：`ec_kafka_consumer_lag` 单调爬升 → 应用日志 `lag=/state still pending/max.poll.interval`（service=ec-payment）→ 审计 `fault_id=F3` 见 deploy v2.3.1（回调线程加远程校验）→ `ec_payment_confirm_pct` 下滑。
- **期望结论**：v2.3.1 回调消费变慢导致积压（不是 5xx）→ 处置：回滚 v2.3.1 或扩容消费者；验证：lag 回落、pending 单清零。

## 剧本四 F4 网关误限流 + 上游单实例剔除（P1）
- **现场**：下单/结算链路 429/502 突增。
- **问**：“刚才一阵下单页全是 429/502，网关是不是有问题？查一下哪些接口、影响谁。”
- **模型应做**：`ec_access_logs` `status in (429,502,503)` 按 path 收敛（/checkout、/orders）→ 看 `ec_http_error_rate{service="ec-product"}` 抬升 → 审计 `fault_id=F4` 见路由权重 100/0 + 误开限流 zone。
- **期望结论**：网关对下单/订单上游误限流并摘除单实例 → 处置：恢复权重 50/50、修健康检查；验证：429/5xx 归零。

## 剧本五 F5 节点磁盘 90% + 外呼证书过期（P2 · 双层告警示范）
- **现场**：系统日志磁盘告警 + 外呼 HTTPS 证书错误，像“两件事”。
- **问**：“节点磁盘告警，同时支付外呼报证书过期，看看是不是两起独立故障。”
- **模型应做**：`ec_node_disk_pct{node="ec-node-2"}` ~92% → `ec_system_logs` WARN/ERROR 见 `No space left/certificate` → 审计见清理 cron 停用 → 关联出“磁盘满 → ACME 写不了 → 证书过期”一条因果链（不是两起）。
- **期望结论**：同一起根因链：磁盘满导致证书无法续期 → 处置：清理 /data/backups、重启 cert-bot、恢复轮转 cron；验证：disk 回落、证书日期恢复。

## 剧本六 F6 前端发版引入 JS 报错（P2 · RUM）
- **现场**：RUM 显示 checkout/首页 JS 报错上升。
- **问**：“发版后前端报错变多了，看看是哪个版本、什么报错、影响哪些页面。”
- **模型应做**：`ec_rum_error` 按 `error_type/route` 收敛（resource 404 + runtime）→ 看 `dist_version` 差异（2.4.0-7f3a vs 2.3.9）→ `ec_rum_js_error_rate` 突升 → 对样 `fault-F6`。
- **期望结论**：灰度 2.4.0 的 index.html 仍引用旧 chunk → 404 JS → 处置：核对 index.html 引用、回滚 2.3.9、清 CDN 缓存；验证：JS error 回落。

## 复盘建议
- 每演一条：对照上面「期望结论」逐项打分（工具使用 / 证据引用 / 根因 / 处置），重点看**模型有没有真查**、**根因链对不对**（尤其 F5 那种“两件事其实一条根因”）。
- 想加压：换一个模型不知道的 live 故障；或把告警触发后立刻问（现场热）；或让它先做 triage 再追问深挖。
- 若模型字段名不对：提醒它先读挂载资料库（02/03）或 StreamSchema —— 这正是整套设计里“防编造字段”的兜底，值得现场演示一遍。
